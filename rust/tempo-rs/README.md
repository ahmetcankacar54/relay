# tempo-rs

Rust port of `shared/tempo.ts`, bridged with napi-rs. Generated by rust-anything; `src/port.rs`
delegates to `relay_core::shared::tempo`, and `src/port/args.rs` turns the bindings' JSON
(`undefined` members, `{"$num": ...}` markers) into the relay-core types.

## Functions

- `presetTempo` (`shared/tempo.ts:28`): the TS defaults (`source = "preset"`, no days) are filled
  when the arguments are missing or `undefined`.
- `fallbackTempo` (`shared/tempo.ts:43`)
- `learnTempo` (`shared/tempo.ts:62`)
- `tempoAt` (`shared/tempo.ts:226`)

`tempoRate` stays in TypeScript here (`js_only`): it returns a lookup function. Its port,
`tempo::tempo_rate`, is checked by the ported unit tests.

## Known differences

An invalid IANA time zone makes the TS throw (`RangeError: Invalid time zone specified`), while
relay-core reads an unknown zone as UTC (store validation never lets one through); the cases use
real zones.

## Loop

Cases are the calls the tests make plus `inputs.jsonl` (every preset with and without its
defaults, the fallback and preset paths of `learnTempo`, and `tempoAt` over a week in five zones).
Generated inputs are off (`--count 0`): they pass arbitrary JSON where the TS types name `Tempo`
and `PlanningSettings`, and junk time zones.

```sh
rust-anything record rust/tempo-rs --count 0 --pin-clock --inputs rust/tempo-rs/inputs.jsonl \
  --from-tests -- node --import tsx --test tests/adaptive-pace.test.ts \
  tests/adaptive-replan.test.ts tests/adaptive-schedule.test.ts tests/day-plan.test.ts \
  tests/day-timeline.test.ts tests/live-forecast.test.ts tests/planning-panel.test.ts \
  tests/selectors.test.ts tests/tempo-tracker.test.ts tests/tempo.test.ts tests/window-keeper.test.ts
rust-anything build rust/tempo-rs
rust-anything diff rust/tempo-rs
rust-anything gate rust/tempo-rs
```
