# Stable local macOS signing

Relay's local signing command uses one existing Code Signing certificate and its
private key in Keychain. It pins the certificate's complete public SHA-1
fingerprint, rather than a potentially duplicated certificate name. The app and
the `desktop-automation` and `usage-keychain` helpers retain their bundle
identifiers and use the normal designated requirements generated by `codesign`.
The command never creates a certificate, imports a private key, changes Keychain
access controls or certificate trust, modifies TCC, or launches Relay or Claude.

## Prepare the identity once

Use an existing Apple Development or Developer ID Application identity when
available. For use on this Mac, Apple's Certificate Assistant can instead create
a self-signed **Code Signing** identity in the login Keychain. Keep its private
key in Keychain and retain the same certificate for subsequent local builds.
A local self-signed certificate establishes continuity between builds; it is
not a Developer ID distribution certificate or a notarization service.

Creating or using the signing key can require a macOS approval. This is separate
from Relay's Accessibility consent and permission to read Claude credential
items. A successful signature does not automatically authorize those resources.
Switching from ad-hoc signing to certificate signing changes the identity once,
so the first certificate build can require new consent. Later builds must satisfy
that build's saved designated requirements. A locked Keychain, revoked consent,
an expired or replaced signing identity, or changes to a credential item's access
policy can still require user action. Never weaken an item's access policy or
trust the certificate for unrelated purposes to suppress an alert.

Store only the public certificate fingerprint in `config/local-signing.json`:

```json
{
  "version": 1,
  "certificateFingerprint": "FULL_40_CHARACTER_PUBLIC_CERTIFICATE_SHA1"
}
```

The private key, certificate export passwords, account tokens, and Keychain
passwords do not belong in this file or the workspace. If a local identity is
not available as a valid Code Signing identity, the command stops. It does not
silently create a new certificate or fall back to ad-hoc signing.

## Build and verify

On macOS `npm run dist` uses this pinned-certificate workflow by default. It
never silently switches back to ad-hoc signing. `npm run dist:mac:local` exposes
the same command explicitly. Other platforms keep their ordinary build path.

```sh
node scripts/stable-signing.mjs --output release/stable-first
```

To supply the public fingerprint explicitly, add `--identity FULL40HEX`.
`--skip-build` packages already built source files; the normal command first
runs the TypeScript, UI, and native build. Only a directory inside this
workspace's `release` directory can be used as build output. Existing `CSC_LINK`,
`CSC_KEYCHAIN`, or `CSC_KEY_PASSWORD` variables are rejected: this path uses the
existing pinned identity and does not perform a Keychain import.

For an update, retain the previous signed app and use a new output directory:

```sh
node scripts/stable-signing.mjs \
  --previous /absolute/path/previous/Relay.app \
  --output release/stable-next
```

The command signs nested code inside out with Electron's ordinary signing
library, preserves hardened runtime and the existing per-file entitlement
policy, and checks the final bundle with deep, strict signature verification.
For a local self-signed identity, it matches the public certificate to the pin
and cryptographically verifies its self-signature before disabling server
timestamping. This avoids a timestamp server dependency for local builds and
long authorization delays. CA-issued Apple Development and Developer ID
identities retain the signing library's ordinary timestamp policy. Certificate
trust, the system clock, and designated requirements are unchanged.
It exports only the public certificates to a temporary private directory and
checks the pinned leaf fingerprint and stable identifiers on the app and both
permission-relevant helpers. The temporary public certificate files are removed.

With `--previous`, each new component must satisfy the old component's designated
requirement, and the old component must satisfy the new requirement. A changed
code hash is allowed; a changed permission identity is rejected. This check
tests update continuity without launching either build or changing macOS
permissions. The JSON report includes the public certificate metadata, each
designated requirement, and code hashes for comparing altered builds.
Signing or verification errors always produce a failed process exit, including
when a native packaging dependency resets the process exit code during cleanup.

To verify an existing app without building or signing it:

```sh
node scripts/stable-signing.mjs --verify /absolute/path/Relay.app
```

## Primary references

- [Apple TN3127: Inside Code Signing — Requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements): macOS records designated requirements when granting privacy access and uses them to identify later versions.
- [Apple TN2206: macOS Code Signing In Depth](https://developer.apple.com/library/archive/technotes/tn2206/): Keychain tracks code identity through designated requirements; self-signed code identities can supply local continuity. Certificate Assistant is the recommended route for creating a new local signing identity.
- [Apple TN3161: Inside Code Signing — Certificates](https://developer.apple.com/documentation/technotes/tn3161-inside-code-signing-certificates): signature integrity validation and distribution suitability are different checks.
- [electron-builder v26 macOS signing](https://www.electron.build/v26/docs/features/code-signing/code-signing-mac/): signing identity configuration and local Electron hardened runtime requirements.
